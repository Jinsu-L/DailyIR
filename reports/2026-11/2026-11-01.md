### 1. ProSearch: Benchmarking Multi-Constraint Protocol Retrieval in Experimental Science

- **LLM Score**: 0
- **Keyword Score**: 24
- **Authors**: Wenliang Liang, Zhiyuan Ning, Haolin Chen, Yuanchun Zhou, Wenjuan Cui, Yi Du
- **URL**: <http://arxiv.org/abs/2610.41396v1>
- **Submitted**: 2026-10-30 08:06:24
- **Comment**: Accepted to NeurIPS 2026 (Evaluations and Datasets Track). 48 pages, 4 figures. Wenliang Liang and Zhiyuan Ning contributed equally. Code: https://github.com/kg4sci/ProSearch. Data: https://huggingface.co/datasets/kg4sci/ProSearch

#### T.A.R.G.E.T. Summary (from Abstract)
- **Topic**: Multi‑constraint protocol retrieval benchmark (ProSearch)
- **Aim**: Provide a systematic, realistic evaluation framework for retrieval systems that must satisfy multiple, interdependent constraints in experimental protocol queries.
- **Rationale**: Existing benchmarks lack realistic, constraint‑rich queries; ProSearch fills this gap by deriving queries from authentic records and expert templates, enabling meaningful assessment of scientific retrieval systems.
- **Ground**: Construction pipeline: 1) LLM‑based extraction of protocol details; 2) Data‑driven selection of salient constraints; 3) Controlled, domain‑specific query generation; 4) Evidence‑based relevance validation. Dataset: 1,515 queries across six experimental domains, covering 60 fields with 3–5 explicit constraints each.
- **Experiment**: Evaluated 19 retrieval systems: baseline nDCG@10 = 0.290, improved to 0.474 after reranking. Diagnostic analysis identified explicit constraint matching as a strong ranking signal; manual error analysis pinpointed joint constraint binding as the main bottleneck.
- **Takeaway**: ProSearch offers a rigorous, diagnostic testbed that highlights the critical role of constraint matching in scientific retrieval, guiding future system development and benchmarking.

#### Abstract
> In AI for Science scenarios, experimental design and method reproduction require retrieving protocols that satisfy multiple interdependent constraints, yet existing benchmarks lack systematic evaluation of this capability. To address this gap, we introduce ProSearch, a benchmark for multi-constraint protocol retrieval in experimental science. ProSearch has three key features: (1) realism, with queries grounded in real experimental records and expert-defined templates; (2) complexity, with 60 experimental fields and their dependencies; and (3) diagnosticity, with 3-5 explicit constraints per query, including numerical and negation constraints. We construct ProSearch through LLM-based extraction, data-driven constraint selection, controlled query generation, and evidence-based relevance validation. The resulting benchmark contains 1,515 queries across six experimental science domains. We conduct extensive experiments on ProSearch with 19 representative retrievers and complementary analyses. The best-performing retriever achieves an average nDCG@10 of only 0.290, which improves to 0.474 with reranking. Structured diagnostic analysis shows that explicit constraint matching provides a strong ranking signal, while manual error analysis identifies joint constraint binding as a key bottleneck. ProSearch provides a testbed for systematically evaluating scientific retrieval systems.

### 2. Defining Page-Centric Visual Document Retrieval and Evaluating Existing Benchmarks

- **LLM Score**: 0
- **Keyword Score**: 21
- **Authors**: Chongzhi Zhang, Yuqi Zuo, Aixin Sun
- **URL**: <http://arxiv.org/abs/2610.41360v1>
- **Submitted**: 2026-10-30 07:24:39
- **Topic Keywords**: information retrieval, query, queries, ranking, relevance, rag, retrieval, rank, search
- **Reason**: LLM scoring failed.

#### Abstract
> In modern information retrieval (IR), documents are increasingly encountered as structured sequences of visually rich, paginated units, rather than as flat text. Example documents encountered in our daily life include Word files, PDFs, and slide decks. Free text-centric retrieval systems either ignore this structure entirely or destroy it through arbitrary passage chunking. In this paper, we formulate page-centric Visual Document Retrieval (VDR) with pages as the fundamental indexing units and document context available for assessing page relevance. The formulation distinguishes two retrieval granularities, page and document, and three retrieval paradigms: independent-item, evidence-set, and iterative retrieval. We then assess 42 benchmarks using eight criteria covering corpus characteristics, query construction, relevance annotation, and ranking support. Our analysis shows two main findings on current VDR research. First, evaluation remains concentrated on page-level independent-item retrieval, with fewer resources supporting document-level, evidence-set, and iterative settings. Second, queries originating from real user information needs independently of target corpus content and graded relevance judgments are uncommon, while the coverage and verification of relevance judgments vary substantially. Both findings reveal gaps between the capabilities applications require and those existing evaluation protocols can establish. We provide benchmark selection guidance and identify priorities for future benchmark design, emphasizing alignment between task requirements, relevance semantics, and evaluation protocols.

### 3. Completeness and Cost of Retrieval Structures for Multi-Tool Requests in LLM Agents

- **LLM Score**: 0
- **Keyword Score**: 15
- **Authors**: Shuyang Zhang
- **URL**: <http://arxiv.org/abs/2610.41905v1>
- **Submitted**: 2026-10-30 15:40:02
- **Comment**: 17 pages, 3 figures, 9 tables
- **Topic Keywords**: retriever, dense retrieval, query, queries, retrieval, rank
- **Reason**: LLM scoring failed.

#### Abstract
> An agent that must call several tools to fulfill a request fails when the tool retriever omits any one of them, yet tool retrievers are mostly built and evaluated on queries requiring a single tool. We compare representatives of six retrieval structures (flat lexical and dense retrieval, LLM query decomposition, LLM-navigated hierarchies, server-then-tool matching, dependency graphs, and trained set-level retrievers) across two multi-tool testbeds: 345 AppWorld queries with expert dependency labels and 103 MCP-Bench tasks over 257 MCP tools. We measure completeness@k, the share of queries whose entire required tool set appears in the top k, alongside the LLM calls, tokens, and latency that each structure incurs at retrieval time. A motivating analysis on all 7,961 ToolRet queries shows that aggregate completeness mixes two regimes: completeness at 10 is .58 to .67 on single-target queries and .08 to .17 on queries with four or more targets, and the ordering of retrievers on single-target queries reverses on multi-target ones. Across the two testbeds, none of the compared structures that is untrained on the testbed and makes at most one LLM call per query completes more than 10% of AppWorld queries at k = 16. The two structures that do better incur different costs: a set-level retriever trained on 75 to 90 in-domain queries reaches .33 on AppWorld and .58 on MCP-Bench with no LLM calls, while an LLM-navigated hierarchy reaches .30 and .40 with a median of 31 to 38 LLM calls and about five minutes per query. Their failure modes also differ: the trained retriever mostly ranks the missing tools just below the cutoff, whereas the hierarchy finds the target API and stops before collecting its prerequisites. In a downstream check with the official AppWorld agent, tasks with a complete retrieved set succeeded 21 of 21 times, whereas incomplete ones succeeded 2 of 39 times.

#### Abstract
> LLM-based theorem proving in Lean 4 has advanced rapidly, but provers are difficult to leverage newly contributed lemmas, because retrieval skews toward popular foundational lemmas, leaving the right premises buried among hundreds of thousands of candidates. #### Abstract
> Retrieval-augmented generation is becoming agentic. A search harness writes queries, reads results, reformulates, and decides when to stop. This largely solves accuracy: a harness with only BM25/grep and MiniMax M3 answers 85% of BrowseComp-Plus and 91% on multi-hop FRAMES in our runs, without compiled or vector indexes. It exposes a context problem: an undisciplined loop repeats queries, rereads documents, and fills the window with unused passages. #### Abstract
> Conversational RAG benchmarks such as MTRAG and RETECO evaluate retrieval and generation end to end: each system answers from its own retrieval, so abstention must be scored against whether each retrieved context is sufficient. A convenient shortcut reads sufficiency off the relevance judgments and treats a context without gold documents as unanswerable. We release code, runs and labels, and recommend scoring refusals against content labels, not the presence of gold.

### 13. Fidelity Synopses: Pre-Execution Plan Selection for Approximate Vector Search

- **LLM Score**: 0
- **Keyword Score**: 7
- **Authors**: Adithya Ramanatha, Sanskar S. Singh, Maya Ramanath
- **URL**: <http://arxiv.org/abs/2610.41407v1>
- **Submitted**: 2026-10-30 08:19:23
- **Topic Keywords**: query, queries, search
- **Reason**: LLM scoring failed.

#### Abstract
> Vector search has become a database operator with many physical implementations: different index families, build-time and search-time parameters, and compressed or disk-resident variants. Each trades cost against fidelity, the fraction of a query's exact top-k nearest neighbors that a configuration returns. Deployments nevertheless choose one configuration offline and use it for every query, so they are sized for their hardest queries and overpay for the rest. On a 5.8M-item LAION benchmark with four embedding models, running each query on the cheapest configuration that suffices for it would roughly halve the cost in a typical setting. Exploiting this requires predicting each configuration's fidelity before running it, which is hard because fidelity is defined by the very exact search that approximate indexes avoid. Relational optimizers solve the analogous problem for cardinality with offline synopses; we propose one for vector search. A fidelity synopsis divides the embedding space into cells around a set of landmarks and records, for every cell and configuration, how often that configuration met a fidelity target on a sample of queries. At query time, one nearest-landmark lookup yields a calibrated estimate for every configuration, and an optimizer chooses configurations so that the workload misses the target no more often than its requirement allows. We test the two premises the synopsis relies on, that fidelity varies smoothly across the embedding space and that its loss is specific to each configuration. Held to the same requirement a static deployment is built to meet, synopsis-guided selection lowers cost in all 16 combinations of model and query direction, to a median of 0.72x the static deployment, with a batched lookup of 21-32 microseconds per query. The saving persists against the best static choice among the same indexes, and within a single index at no extra memory.

### 1. Octen-WebGR: Scaling Generative Retrieval to 200 Million Web Pages

- **LLM Score**: 0
- **Keyword Score**: 18
- **Authors**: Guangwei Xu, Wenkai Zhang, Yawen Liu, Dongxu Zhang, Xijie Xu, Kuan Zou
- **URL**: <http://arxiv.org/abs/2610.35256v1>
- **Submitted**: 2026-10-26 11:39:04
- **Topic Keywords**: retriever, dense retrieval, query, queries, click, retrieval, rank, search
- **Reason**: LLM scoring failed.

#### T.A.R.G.E.T. Summary (from Abstract)
- **Topic**: Generative Retrieval for Large-Scale Navigational Search (Octen‑WebGR)
- **Aim**: Enable a retrieval system that generalizes to unseen queries and pages by embedding web‑page representations inside a language model and generating constrained semantic identifiers for exact URLs.
- **Rationale**: Click‑table systems excel on seen queries but fail to generalize; dense embedding retrievers generalize across content but rank navigational targets poorly. Constrained generation leverages a model’s generative capacity while still pointing to exact pages, combining the strengths of both approaches.
- **Ground**: Store 201 million page representations in a 4‑billion‑parameter LM; for each query the model generates a two‑token identifier that is mapped to a pre‑computed URL table, turning retrieval into a constrained generation problem.
- **Experiment**: Evaluated on real navigational traffic one month after training: Top‑1 accuracy 59.6% for Octen‑WebGR vs 46.5% for click‑enhanced dense retriever and 37.5% for LLM memory baseline. Query‑generalization: 30.9% correct first rank vs 17.2% for dense retriever (21.4% with click prior). Page‑generalization: dense retrieval better on rarely visited pages. Resource efficiency: 4B model runs on a single GPU with 10 GB memory versus 412 GB for exact dense retrieval. Scaling experiments up to 32 M URLs show sublinear growth in model size; performance limited by page exposure rather than capacity.
- **Takeaway**: Constrained generative retrieval achieves higher accuracy, better query generalization, and far lower memory usage than dense retrieval, while dense methods still excel on rarely visited pages. The complementary strengths suggest hybrid systems and demonstrate that generative models can efficiently index and retrieve large web corpora.

#### Abstract
> Navigational search aims to find a single target page among hundreds of millions of web pages. Click tables work well for queries seen before but cannot generalise to new formulations, while embedding retrievers generalise across content but often rank navigational targets poorly. We introduce Octen-WebGR, a generative retrieval framework that stores web pages in the parameters of a language model: given a query, the model generates a two-token semantic identifier constrained to a table of real URLs. We develop Octen-WebGR-4B, which indexes 201 million web pages, and evaluate it on real navigational traffic from the month after training. Generative retrieval is most effective on new ways of asking for familiar pages: for unseen queries targeting pages with substantial interaction history, it ranks the correct page first 30.9% of the time, against 17.2% for a dense retriever trained on the same clicks (21.4% with a click prior). Embedding retrieval keeps an advantage on rarely visited pages, so the two approaches generalise on complementary sides, the query and the page. Over all navigational traffic, Octen-WebGR reaches 59.6% top-1 accuracy, against 46.5% for a click-enhanced dense retriever and up to 37.5% for frontier LLMs answering from memory, which cost at least 40 times as much per query. The 4B model runs on a single GPU with 10 GB of memory, compared with 412 GB for exact dense retrieval. Scaling experiments with up to 32 million URLs show that, when every query-page pair is seen equally often, the model size needed grows sublinearly with index size, and that retrieval is constrained more by page exposure than by model capacity. We release Octen-WebGR-4B and Octen-WebGR-0.6B with their identifier tables and inference code.

### 5. Agent Memory as Recommendation: Recommender-System Design for Long-Term Memory of LLM Agents

- **LLM Score**: 0
- **Keyword Score**: 13
- **Authors**: Xinyu Zhang, Weiwei Sun
- **URL**: <http://arxiv.org/abs/2610.34673v1>
- **Submitted**: 2026-10-26 01:05:20
- **Comment**: 12 pages, 3 figures, 8 tables
- **Topic Keywords**: query, rerank, learning to rank, rag, recommend, rank
- **Reason**: LLM scoring failed.

#### Abstract
> Large language model (LLM) agents that serve users across many sessions must choose, for every request, the few stored memories that enter a limited context window. This choice largely decides whether the agent answers correctly, and it runs on every request at Web scale. This selection faces three challenges: a large and growing store, a per-request cost budget, and multi-session questions that need all of their evidence. Many memory systems build notes or graphs with hundreds to thousands of LLM calls per history, and each is designed on its own, so it is unclear which component yields the accuracy. These challenges mirror the properties of recommendation, so we formalize agent memory as budgeted slate recommendation, with the request as the user, stored memories as items and the context window as a slate. The formalization places memory systems in one design space of recommender cascades and factorizes accuracy into the completeness that each stage controls. Guided by it, we propose AgentMemRec, which adapts candidate generation, learning to rank and slate construction from recommender systems and selects memories without any LLM call. On multi-session questions of LongMemEval, AgentMemRec outperforms memory and context-selection methods, including A-Mem, HippoRAG 2, DynamicRAG and T-Mem, by 10 to 31 points of accuracy. It matches an LLM reranker that makes 64 calls per query at 3.2 times lower serving cost, and on LoCoMo it outperforms Mem0 and Zep without any LLM call at write time. The factorization attributes the gains to slates that more often hold all of the evidence, so recommender-system design offers an effective and efficient foundation for the long-term memory of LLM agents.

- **URL**: <http://arxiv.org/abs/2610.35142v1>
- **Submitted**: 2026-10-26 10:11:24
- **Comment**: 12 pages, 10 figures
- **Topic Keywords**: query, queries, rag, retrieval, web search, search

#### Abstract
> Large language models (LLMs) often produce plausible but incorrect answers, motivating reinforcement learning methods that reward correct answers, penalize incorrect answers, and allow abstention. However, fixed outcome-based rewards do not distinguish incorrect responses with different confidence levels or account for differences in answering reliability across queries. Consequently, such rewards may inadequately penalize overconfident errors and fail to discourage unnecessary abstention. We propose CalibraRL, a reinforcement learning framework that incorporates response confidence and query-level answering evidence into reward design. For non-abstaining responses, CalibraRL combines correctness-based utility with a Brier-based penalty that encourages agreement between confidence and correctness. For abstentions, it estimates conditional answering reliability using a Beta posterior derived from the correctness of non-abstaining responses within each sampled group. The abstention reward increases with the posterior probability that the model's accuracy on non-abstaining responses is below a predefined threshold. CalibraRL reuses training rollouts without requiring additional annotations indicating whether the model knows the answer to each question. Experiments on three QA datasets demonstrate that CalibraRL improves answer precision and reduces hallucinations compared with strong baselines. Further analysis shows that CalibraRL reduces mean expected calibration error (ECE) by 30.8\% across two backbone models and three datasets, highlighting its potential to improve the reliability of retrieval-augmented generation (RAG) in web search.

#### Abstract
> Graph-based retrieval-augmented generation (GraphRAG) answers multi-hop questions by organizing a corpus into a graph and retrieving along its structure. #### Abstract
> Query-time filters that screen each retrieved document before it reaches the generator are the dominant published defense against retrieval-augmented generation poisoning, and they report near-perfect detection on domain benchmarks.
